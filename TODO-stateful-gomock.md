# Stateful gomock — разработка подхода для тестов «gomock + состояние»

## Проблема

В этом репозитории тесты к одному и тому же коду написаны двумя способами:

- **`app_test.go`** — использует `go.uber.org/mock/gomock`.
  Масштабируется: можно добавить любой новый метод и тест, сложность остаётся
  на том же уровне. Но тесты сложно читать: все вызовы мока задаются
  последовательно через EXPECT, и чтобы понять, что делает тест,
  нужно в голове симулировать состояние мира, которое эти вызовы
  накапливают. Это очень быстро становится нечеловеческим.

- **`app_world_test.go`** — использует самодельный stateful mock,
  где мок сам следит за состоянием мира (смонтировано ли, какие файлы
  существуют, какие программы приаттачены).
  Код тестовых функций стал простым и читаемым, но:
  - Все «что может пойти не так» закодировано в виде двух десятков
    полей `worldState` (20+ полей, каждое с уникальным поведением).
    Это уже опасно близко к антипаттерну God Object.
  - Невозможно задать последовательность: метод либо всегда падает
    с ошибкой (`faults.mkdir = err`), либо никогда.
  - При масштабировании приложения количество полей и специальных
    случаев будет только расти. На тривиальном приложении уже тесно,
    подход в целом не масштабируется.

**Нужно:** что-то среднее — состояние мира (как в `app_world_test.go`)
плюс ключевые фичи gomock (очередь вызовов, инъекция данных, а не только ошибок).

## Что перепробовали

### 1. Разделение worldState на state + faults

Первый рефакторинг: разбили монолитный `worldState` на две части:

- `worldState` — только состояние: euid, mounted, fs (MapFS),
  tempFiles, attached, markBytes.
- `faults` — только error-инъекции: mkdir, mount, createTemp и т.д.

Плюс: тесты стали чище, видно «что настраивает состояние» vs «что фейлится».
Минус: это не решает проблему God Object (20 полей → 10 + 10),
и не решает проблему последовательности.

### 2. Generic-подход (отвергнут)

Было предложение сделать generic-тип `Next[F any]` с методами `Push`/`Pop`,
по одному типу на каждую сигнатуру метода World. Для 6 сигнатур пришлось
бы завести 6 generic-типов с 3 хелперами каждый — ~80 строк шаблонного кода.

Плюс: типизированная очередь для каждого метода, полная type safety.
Минус: много дублирования, комбинаторный взрыв, при добавлении новых
сигнатур пришлось бы писать ещё один блок.

### 3. Reflect-подход (текущий, принят)

Один внутренний механизм на reflect. Два внешних типа:

- **`stubE`** — для методов с сигнатурой `f(args) error`
  (`OsMkdirAll`, `OsRemove`, `OsRemoveAll`)
- **`stubRE[R]`** — для методов с сигнатурой `f(args) (R, error)`
  (`OsStat`, `OsCreateTemp`, `OsCreateTemp`)
- **`stubR[R]`** — для методов с сигнатурой `f(args) R`
  (`OsGeteuid`)
- **`stubV`** — для void-методов `f(args)`
  (пока не используется в World, но для полноты)

Каждый stub:

- Хранит очередь `func([]reflect.Value) []reflect.Value` и `defCall`.
- Конструктор `newStubX(def)` принимает дефолтную реализацию,
  сохраняет её как reflect-callable.
- `Fail(err)` — вернуть ошибку (есть у stubE, stubRE).
- `Returns(...)` — вернуть заданные значения.
- `Default()` — вставить в очередь вызов дефолта.
- `Call(args...)` — вызвать следующий из очереди или дефолт.
- Если очередь пуста — всегда вызывается дефолт.

Плюсы:

- Никакого комбинаторного взрыва: 4 типа на все случаи,
  внутренний механизм един на всех.
- Стейт-тесты читаемые: `t.World.mkdirStub.Fail(err)`.
- Есть sequence: `Fail → Returns → Default → пусто → дефолт`.
- Производительность reflect неважна для тестов.
- При добавлении нового метода в World: добавляем stub-поле в mockWorld,
  дефолтную имплементацию, и однострочный метод мока через `Call`.

## Текущее состояние

- ✅ stub-реализация вынесена в отдельный пакет `test/stub/`
  с экспортированными API (`StubE`, `StubRE`, `StubR`, `StubV`).
- ✅ stub-тесты переписаны как внешние (`package stub_test`),
  через `t.Err`, с проверкой множественных вызовов.
- `app_world_test.go` пока не переделан на stub-механику —
  использует старые `faults`.

## План

1. Вынести stub-реализацию в `test/stub/` с экспортированными типами
   (`StubE`, `StubRE`, `StubR`, `StubV` и конструкторами `NewStubE(def)`, ...).
2. Тесты к stub — как внешние (`package stub_test`).
3. Создать третий файл `app_stub_test.go`, где:
   - `faults` удалён целиком.
   - mockWorld использует StubE / StubRE / StubR.
   - Каждый метод мока — однострочник `return m.xxxStub.Call(args...)`.
   - Тесты используют `t.World.xxxStub.Fail(...)` / `.Returns(...)` / `.Default()`.
4. Сравнить читаемость с `app_test.go` (gomock) и `app_world_test.go` (faults).
